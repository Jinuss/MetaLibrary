# 民生公众号文章写作

## 这个 Skill 解决什么问题

把一件与普通人生活相关的事，讲得**准确、清楚、可信、好读**，并且让人在微信搜一搜里搜得到。民生内容的读者不关心文采，只关心两件事：**这事和我有什么关系**、**我该怎么办**。

因此一切写作决策都服从四条：事实站得住、话说得明白、读起来不累、搜得到。

## 何时使用

- 用户要写一篇民生方向的公众号文章，含选题、大纲、初稿、成稿任一环节
- 用户给出零散素材（政策文件、新闻、网友提问），要求整理成可发布的图文
- 用户要求核查已有文章的事实、信源、数据准确性
- 用户要求「去 AI 味 / 太像机器写的 / 太啰嗦 / 排版难看 / 搜不到」
- 用户提供历史文章，要求按其风格仿写民生内容

**不适用**：纯营销软文、娱乐八卦、无事实基础的虚构故事、需要涉政敏感议题评论（遇此类需求直接说明不适用，建议改选题）。

## 六条硬底线

写作过程中任何一条被破坏，都要推倒重来，不接受「整体还不错」。

1. **可回溯**：每一个事实、数字、政策条款，都能指名道姓落到一份文件、一次发布会、一个官方链接上。查不到出处的，删掉，不写「据了解」。
2. **不改口径**：政策原文怎么表述就怎么复述。原文说「符合条件的人员」，就不能写成「所有人都能」；原文说「逐步推进」，就不能写成「马上落地」。不缩水，不放大。
3. **一句话能说清就不用两句**：写完每段自问「删掉这句，信息有没有损失」。没有损失就删。
4. **像人说话**：句子有长有短，段落有疏有密。不出现模板句式、排比填空、对仗口号。
5. **读者视角优先**：先讲「对读者意味着什么」，再讲「政策是怎么规定的」。不写成文件转述。
6. **标题、摘要、首段都要能被搜到**：这三个位置是微信搜一搜的抓手，必须自然嵌入读者会真实输入的词。

详细规则见对应 reference，不要凭印象写。

## 标准工作流

按顺序执行。第 2 步与第 4 步需要用户确认后再继续。

### Step 1 · 采集事实 → `references/source-standards.md`

先搜信源，再动笔。顺序不能反。

1. 确定这件事的**一手出处**：发文机关、文件全称、发布日期、生效日期、有效状态。
2. 需要的数据（人数、金额、比例、时限）必须找到原始发布口径，不用二手转述的数字。
3. 记录每条事实的来源，形成来源清单，随稿交付。
4. 信源冲突时，以官方一手为准，并在文中说明差异而非回避。

信源分级、检索渠道、核验清单见 `references/source-standards.md`。

### Step 2 · 定选题与结构（需用户确认）

1. 用一句话说清：**这篇文解决读者的哪个具体疑问**。说不清就是选题没定。
2. 判断读者最可能输入什么搜索词，这决定了标题的骨架。
3. 产出大纲：3-5 个小节，每节一句话概括，标明哪节是重点。
4. 把选题角度、大纲、拟用标题方向交给用户确认。确认后再写，避免整篇重来。

### Step 3 · 写初稿 → `references/writing-rules.md`

按大纲落笔，严格要求：

- 开头 100 字内点明「这件事和读者有什么关系」，不要铺垫、不要背景长镜头、不要「近年来……」
- 每个小节只解决一个问题，小节内不跑题
- 复杂概念先给类比或场景，再给准确表述
- 涉及读者要办的事，写成可执行的动作（找谁、带什么、去哪、多久）
- 全文出现的关键词保持统一表述，不换同义词，方便检索

用词红线、结构模板、句式禁忌见 `references/writing-rules.md`。

### Step 4 · 去 AI 味与精简（需用户确认差异）

对初稿做三遍处理，每遍只盯一件事：

1. **删**：删掉不承载信息的过渡句、总结句、「值得注意的是」类提示语、重复表述。目标砍掉 15%-30% 字数。
2. **换**：把抽象换成具体，把被动换成主动，把名词堆叠换成动词短句。替换掉 AI 高频词。
3. **读**：逐段默读，凡是舌头打结的地方就是语句不通顺，改到能一口气读完。

两遍处理的具体手法与禁用词表见 `references/writing-rules.md`。改写幅度较大时，向用户说明改了哪些地方。

### Step 5 · 检索优化与排版 → `references/wechat-seo.md` + `references/layout-guide.md`

1. 生成 5-8 个标题候选，按检索命中与可读性打分，推荐一个主标题，另附一个稳妥版、一个传播版。
2. 写摘要（≤120 字），前 30 字必须含核心关键词。
3. 检查正文首段、小标题、结尾是否自然覆盖关键词，密度控制在 5% 以内。
4. 给出话题标签建议、封面图文案建议、封面尺寸建议。
5. 按排版规范产出 HTML 交付页，以 `assets/wechat-article-template.html` 为骨架：完整 HTML 文档 + 全内联样式 + 顶部「一键复制到微信」按钮。保存为 UTF-8（不加 BOM），输出到 `article/` 根目录，用户用浏览器打开后点按钮即可粘贴进公众号后台。

平台硬性限制与检索机制见 `references/wechat-seo.md`；字号、间距、加粗、配图规则见 `references/layout-guide.md`。

### Step 6 · 终检

```
python scripts/selfcheck.py <正文文件路径> --title "<标题>" --digest "<摘要>"
```

脚本会检查标题/摘要字数、段落长度、句长分布、AI 味词命中、全半角标点、关键词覆盖等，输出问题清单。逐条处理完再交付。

## 交付物

默认交付以下内容。**文章文件统一输出到 `article/` 根目录**，主文件命名 `YYYY-MM-DD-主题.html`，同名 `.md` 作为纯文本版。

| 项目 | 说明 |
| --- | --- |
| 文章正文 | HTML 一键复制页（浏览器打开 → 点按钮 → 粘贴进公众号后台）+ Markdown 纯文本版 |
| 标题 | 5-8 个候选，标注推荐项与理由 |
| 摘要 | ≤120 字，含核心关键词 |
| 封面建议 | 尺寸规格 + 画面文案 |
| 话题标签 | 3-6 个，参与检索 |
| 来源清单 | 每条事实对应的文件/链接/日期 |
| 自检报告 | 脚本输出 + 处理结论 |

用户要求发布到草稿箱时，再走 `mp-draft-push` 流程，不要默认发布。

## 质量自检问题（交付前逐条回答）

1. 文章里每个数字，我能立刻说出它出自哪份文件吗？
2. 有没有哪句话，删掉之后读者得到的信息变少了？如果都没有，说明写太水。
3. 把文章念一遍，有没有哪句读起来别扭、需要回读？
4. 标题里有没有读者真实会搜的词？还是只有我自己觉得好？
5. 读者读完，知不知道自己下一步该做什么？
6. 有没有哪一处，我在替官方下结论，而原文并没有这么说？
